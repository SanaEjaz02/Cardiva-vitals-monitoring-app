## FYP I Remarks

The following remarks were given during the FYP-I design phase evaluation. Each remark is listed below along with the corrective action taken.

| # | Remark | Response / Action Taken |
|---|--------|------------------------|
| 1 | Title is changed: "Pre-Consultancy Vitals Monitoring System" to "CARDIVA: An IoT wearable for heart Health Risk Analysis" | Acknowledged and updated. The project title has been formally changed to **CARDIVA: An IoT Wearable for Heart Health Risk Analysis** across all documentation, diagrams, and the application itself. The new title accurately reflects the system's core purpose — continuous cardiac vitals monitoring via a wearable IoT device with AI-driven health risk classification and emergency response. |
| 2 | Update the use case diagram accordingly | Revised. The use case diagram has been updated to align with the new project scope and title. It now correctly captures all primary use cases: Monitor Vitals in Real-Time, Detect Fall, Classify Health Risk (Normal / Vitals Alert / Fall Alert / Emergency), Trigger Emergency Alert, View Vitals History, Generate Health Report, Manage Profile, and Consult AI Health Assistant. The diagram also reflects the corrected actors and system boundaries as per remarks 5 and 9 below. |
| 3 | Mention datasets | Added. The system uses two forms of datasets: (1) **Medical threshold datasets** — clinically established normal ranges for Heart Rate (per activity context: resting, walking, running, lying), SpO2 (≥95% normal, <90% emergency), HRV (>50ms normal, <20ms emergency), and Respiration Rate (12–20 breaths/min normal, <5 or >30 emergency), which serve as the rule-based classification baseline; and (2) **Trained ML datasets** — labeled vital reading records used offline in Python (scikit-learn) to train the Emergency Classifier and Fall Detector models, which were then exported and integrated into the app for on-device inference. |
| 4 | Mention machine learning algorithm | Specified. Two ML models are integrated into the system: (1) an **Emergency Classifier** using a Decision Tree / Random Forest algorithm trained on a 7-dimensional feature vector — Heart Rate, SpO2, HRV, Respiration Rate, Weight, Height, and BMI — to predict whether a set of vitals constitutes a high-risk emergency; and (2) a **Fall Detector** that combines accelerometer magnitude heuristics with a trained classifier. Both models are trained offline in Python using scikit-learn, exported as `.pkl` files, and converted to pure Dart code via the `m2cgen` library, enabling on-device inference without a TensorFlow Lite dependency. A rule-based fallback (`VitalClassifier`) is retained as a safety net if model inference fails. |
| 5 | Chatbot cannot be an actor | Corrected. The AI Health Chatbot (CARDIVA Assistant) has been reclassified and is no longer shown as an actor in the use case or sequence diagrams. It is now represented as an internal system feature — a use case titled *"Consult AI Health Assistant"* that the **Patient** actor interacts with. Internally, it is implemented as a `ChatbotEngine` (keyword-driven with planned Groq LLM integration) that operates as a service, not an independent actor. |
| 6 | Change the name of attendant | Updated. The term *"Attendant"* has been renamed to **Emergency Contact** throughout the system, codebase, documentation, and all diagrams. Emergency Contacts are persons registered by the Patient who receive automated SMS/WhatsApp alerts when a health emergency is detected. Each user may register multiple Emergency Contacts, designating one as primary, with individual notification toggles per contact. |
| 7 | Explore the database used | Documented. The system employs a three-tier database architecture: (1) **Firebase Firestore** (NoSQL, cloud) — stores user profiles, emergency contacts, chat sessions, analysis history, and generated health reports in real time; (2) **Supabase (PostgreSQL)** (relational, cloud) — stores structured vital readings, health events, and alert records in normalized tables (`users`, `vital_readings`, `health_events`, `alerts`, `emergency_contacts`), designed for longitudinal data analysis and reporting; and (3) **SharedPreferences** (local, device) — acts as an inter-isolate bridge for the background health monitoring service, temporarily holding readings when the app is closed until they can be synced to the cloud. Firebase Storage is used for profile images and PDF health reports. |
| 8 | Revise sequence diagram | Revised. The sequence diagram has been redrawn to accurately depict the full monitoring pipeline in correct order: (1) Wearable / MockDataService emits a vital reading every 2 seconds → (2) `HealthStatusEngine` runs the 4-class decision matrix (Fall × Vitals risk) → (3) `ConfidenceEngine` computes a 0–100 risk score → (4) UI is updated with the new health status badge and vital cards → (5) if the event requires action, `EmergencyTrigger` captures GPS via `LocationService`, dispatches alerts via `SmsService` (WhatsApp/SMS), pushes a local notification, and saves the alert record to Firestore and Supabase. All interactions across the app, engine, services, and cloud layers are correctly numbered and sequenced. |
| 9 | 2 actor cannot be used in sequence diagram | Corrected. The sequence diagram now shows a single initiating actor: the **Patient**. The Emergency Contact is represented as a passive external recipient who receives outbound SMS/WhatsApp notifications — not as an initiating actor. All internal system components (App UI, HealthStatusEngine, MlService, Firebase, SmsService, LocationService) are shown as lifelines, keeping the actor count to one as required. |
| 10 | Suggestion: Don't reinvent — take OpenWatch and do reverse engineering | Acknowledged and incorporated. The OpenWatch open-source wearable platform was studied. Rather than designing proprietary hardware from scratch, the `BleService` in CARDIVA is architected to communicate with off-the-shelf BLE health wearables using standard BLE GATT profiles for Heart Rate (UUID 0x180D) and SpO2 characteristics. The `MockDataService` mirrors the same data packet structure so that switching from simulation to a real BLE wearable requires only activating the `BleService`, with no changes to the engine, providers, or UI layers. |
